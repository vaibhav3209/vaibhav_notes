??? note "Second Highest Salary"
    <a id="leetcode-176"></a>


    | Approach            | Time Complexity | Handles Duplicates | Handles NULL |
    |---------------------|---|---|---|
    | 1. LIMIT/OFFSET     | O(N log N) | Only with `DISTINCT` | ❌ No |
    | 2. MAX() < MAX()    | O(N) + O(N) | ✅ Yes | ✅ Yes |
    | 3. DENSE_RANK()     | O(N log N) | ✅ Yes | ❌ No |
    | 4. Functional (UDF) | O(N log N) | ✅ Yes (via DISTINCT) | ⚠️ Depends on `WHERE` clause |
    
    
    !!! tip "Best Practice"
        Always add `WHERE salary IS NOT NULL` before ranking or ordering — every approach here can 
        be tripped up by NULLs. (EXCEPT 2nd).
    
    
    === "**Approach 1**: LIMIT AND OFFSET"
    
        ```sql
            SELECT DISTINCT salary
            FROM Employee 
            ORDER BY salary DESC 
            LIMIT 1 OFFSET 1;
        
            /*
                1. Time: O(N log N) .
                2. Handles Duplicates : only if you write `DISTINCT`.
                3. Handles Null: No — if NULLs sort first in your DB, the "first" row could be NULL,
                    throwing off the offset.
                "Why DISTINCT?"
                    If the top salary appears twice, the "2nd row" is just a duplicate of the 1st — 
                    not actually the second distinct salary.
            
                "What if there's only one salary and we OFFSET?"
                    The query just returns `NULL`.
            */
        ```
    
    === "**2**: MAX() < MAX()"
    
        ```sql
            SELECT MAX(salary) AS SecondHighestSalary
            FROM Employee
            WHERE salary < (SELECT MAX(salary) FROM Employee);
        
        /*
            1. Time: O(N) + O(N) — two table scans.
            2. Handles Duplicates : the `<` comparison naturally drops every row equal to
                the top value, ties or not.
            3. Handles Null:`MAX()` ignores NULLs automatically, so a NULL row
                    never "wins" as the max.
          
        */
        ```
    
    === "**3**: DENSE_RANK()"
    
        ```sql
            SELECT salary
            FROM (
                SELECT salary,
                       DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
                FROM Employee
                WHERE salary IS NOT NULL
            ) ranked
            WHERE rnk = 2;
            
            /*
                1. Time:   O(N log N) due to sorting.
                2. Handles Duplicates :Yes — assigns correct, gapless ranks.
                3. Handles Null: No — needs an explicit `WHERE salary IS NOT NULL`.
            
                 "Why not RANK() OVER()?"
                    Ties share a rank and the next rank is skipped (1, 1, 3, 4...).
                     If two people tie for 1st, there's no rank 2 at all — the query returns empty.
            */
        ```
    
    
    === "**4**: Functional (UDF)"
    
        ```sql
            CREATE FUNCTION getNthHighestSalary(N INT) RETURNS INT
            BEGIN
                DECLARE val INT;
                SET val = N - 1;
                RETURN (
                    SELECT DISTINCT salary 
                    FROM Employee 
                    WHERE salary IS NOT NULL
                    ORDER BY salary DESC 
                    LIMIT 1 OFFSET val
                );
            END
    
        /*
            1. Time: O(N log N) due to sorting,
            2. Handles Duplicates : Yes, via `DISTINCT`.
            3. Handles Null: Only if you remember the `WHERE` clause — 
                easy to forget since it's buried inside a function body.
        */
        ```

??? note "Rank w/o Window()"
    <a id="leetcode-178"></a>

    **Implement Rankings without using Window()**

    A rank of a value is just: *"how many distinct/total values are greater than or equal to it?"*

    **Given Table:**

    | id | score |
    |---|---|
    | 1 | 3.50 |
    | 2 | 3.65 |
    | 3 | 4.00 |
    | 4 | 3.85 |
    | 5 | 4.00 |
    | 6 | 3.65 |

    | Method | Ties Behavior | Comparison Sign | Needs DISTINCT |
    |---|---|---|---|
    | DENSE_RANK() equiv | Ties share rank, no gaps | `>=` | ✅ Yes |
    | RANK() equiv | Ties share rank, gaps after | `>=` or `>` (+1) | ❌ No |
    | ROW_NUMBER() equiv | Every row unique, tiebreak by `id` | `>` or `=` with `id` tiebreak | ❌ No |

    === "**Method 1**: DENSE_RANK() equivalent"

        **Technique A — Correlated Subquery** (no `GROUP BY`, `>=` sign)

        ```sql
        SELECT s1.score, 
               (SELECT COUNT(DISTINCT s2.score) 
                FROM Scores s2 
                WHERE s2.score >= s1.score) AS denserank
        FROM Scores s1
        ORDER BY s1.score DESC;
        ```
    
        **Technique B — Self JOIN** (with `GROUP BY`, `>=` sign, `DISTINCT`)
    
        ```sql
        SELECT s1.score
            , COUNT(DISTINCT s2.score) AS denserank
        FROM Scores s1
        LEFT JOIN Scores s2 ON s1.score <= s2.score
        GROUP BY s1.score
        ORDER BY s1.score DESC;
        ```
    
        !!! tip "Core idea"
            Count how many *distinct* scores are ≥ this one — `DISTINCT`
            collapses ties into one rank.

    === "**2**: RANK() equivalent (skips after ties)"

        **Technique A — Self Join** (`>=` sign, no `DISTINCT`)

        ```sql
        SELECT
            s1.score,
            COUNT(*) AS rank
        FROM scores s1
        JOIN scores s2
            ON s2.score >= s1.score
        GROUP BY s1.score
        ORDER BY s1.score DESC;
        ```

        **Technique B — Correlated Subquery** (`>` sign, `+1`)

        ```sql
        SELECT
            s1.score,
            1 + (
                SELECT COUNT(*)
                FROM scores s2
                WHERE s2.score > s1.score
            ) AS rank
        FROM scores s1
        ORDER BY s1.score DESC;
        ```

        !!! tip "Core idea"
            Count rows *strictly greater*, then add 1 — no `DISTINCT`
                needed since ties naturally get the same rank.

    === "**3**: ROW_NUMBER() equivalent"

        Every row gets a unique, sequential number — ties are 
            broken by a deterministic tiebreaker (here, `id` ascending).

        **Technique A — Self Join**
        
        ```sql
        SELECT
            s1.score,
            COUNT(*) AS row_num
        FROM scores s1
        JOIN scores s2
            ON s2.score > s1.score
            OR (s2.score = s1.score AND s2.id <= s1.id)
        GROUP BY s1.score
        ORDER BY s1.score DESC;
        ```

        **Technique B — Correlated Subquery**

        ```sql
        SELECT
            s1.score,
            (
                SELECT COUNT(*)
                FROM scores s2
                WHERE s2.score > s1.score
                   OR (s2.score = s1.score AND s2.id <= s1.id)
            ) AS row_num
        FROM scores s1
        ORDER BY s1.score DESC;
        ```

        !!! tip "Core idea"
            The `id` tiebreaker is what forces uniqueness — without it,
            tied scores would get the same "count," which isn't a true ROW_NUMBER().

??? note "Gaps & Islands"
    <a id="leetcode-180"></a>

[//]: # (Leave one indent for note)
    
    === "For Integer Records"
    
        Integers 1–15, with 3, 7, 8, and 13 removed:
    
        | integer_id |
        |------------|
        | 1  |
        | 2  |
        | 4  |
        | 5  |
        | 6  |
        | 9  |
        | 10 |
        | 11 |
        | 12 |
        | 14 |
        | 15 |
    
        **Problem 1: Finding islands (consecutive runs)**
    
        ```sql
        WITH CTE_ISLANDS AS (
            SELECT
                integer_id,
                integer_id - ROW_NUMBER() OVER (ORDER BY integer_id) AS island_key
            FROM integer_table
        )
        SELECT
            MIN(integer_id) AS island_start,
            MAX(integer_id) AS island_end
        FROM CTE_ISLANDS
        GROUP BY island_key
        ORDER BY island_start;
        ```
    
        **Result:**
    
        | island_start | island_end |
        |--------------|------------|
        | 1  | 2  |
        | 4  | 6  |
        | 9  | 12 |
        | 14 | 15 |
    
        **Problem 2: Finding gaps**
    
        ```sql
        WITH CTE_GAPS AS (
            SELECT
                integer_id,
                LEAD(integer_id) OVER (ORDER BY integer_id) AS next_integer
            FROM integer_table
        )
        SELECT
            integer_id + 1 AS gap_start,
            next_integer - 1 AS gap_end
        FROM CTE_GAPS
        WHERE next_integer <> integer_id + 1;
        ```
    
        **Result:**
    
        | gap_start | gap_end |
        |-----------|---------|
        | 3  | 3  |
        | 7  | 8  |
        | 13 | 13 |
    
    
    === "For Date Records"

        Dates 2024‑01‑01 to 2024‑01‑15, with the 3rd, 7th, 8th, and 13th removed:
    
        | event_date |
        |------------|
        | 2024-01-01 | 
        | 2024-01-02 |              
        | 2024-01-04 |
        | 2024-01-05 |
        | 2024-01-06 |
        | 2024-01-09 |
        | 2024-01-10 |
        | 2024-01-11 |
        | 2024-01-12 |
        | 2024-01-14 |
        | 2024-01-15 |
    
        **Problem 1: Finding islands (consecutive date runs)**
    
        ```sql
        WITH CTE_ISLANDS AS (
            SELECT
                event_date,
                DATEADD(day, -ROW_NUMBER() OVER (ORDER BY event_date), event_date) AS island_key
            FROM date_table
        )
        SELECT
            MIN(event_date) AS island_start,
            MAX(event_date) AS island_end
        FROM CTE_ISLANDS
        GROUP BY island_key
        ORDER BY island_start;
        ```
    
        **Result:**
    
        | island_start | island_end |
        |--------------|------------|
        | 2024-01-01 | 2024-01-02 |
        | 2024-01-04 | 2024-01-06 |
        | 2024-01-09 | 2024-01-12 |
        | 2024-01-14 | 2024-01-15 |
    
        **Problem 2: Finding gaps**
    
        ```sql
        WITH CTE_GAPS AS (
            SELECT
                event_date,
                LEAD(event_date) OVER (ORDER BY event_date) AS next_date
            FROM date_table
        )
        SELECT
            DATEADD(day, 1, event_date) AS gap_start,
            DATEADD(day, -1, next_date) AS gap_end
        FROM CTE_GAPS
        WHERE next_date <> DATEADD(day, 1, event_date);
        ```
    
        **Result:**
    
        | gap_start | gap_end |
        |-----------|---------|
        | 2024-01-03 | 2024-01-03 |
        | 2024-01-07 | 2024-01-08 |
        | 2024-01-13 | 2024-01-13 |

        | integer_id |
        |------------|
        | 1  |
        | 2  |
        | 2  |
        | 4  |
        | 5  |
        | 6  |
        | 9  |
        | 10 |
        | 11 |
        | 12 |
        | 12 |
        | 12 |
        | 13 |
        | 14 |
        | 15 |
    
    
        (row_number shown alongside for clarity, showing the wrong `island_key`):
    
        | integer_id | row_number | island_quantity |
        |------------|------------|------------------|
        | 1  | 1  | 0  |
        | 2  | 2  | 0  |
        | 2  | 3  | -1 |
        | 4  | 4  | 0  |
        | 5  | 5  | 0  |
        | 6  | 6  | 0  |
        | 9  | 7  | 2  |
        | 10 | 8  | 2  |
        | 11 | 9  | 2  |
        | 12 | 10 | 2  |
        | 12 | 11 | 1  |
        | 12 | 12 | 0  |
        | 13 | 13 | 0  |
        | 14 | 14 | 0  |
        | 15 | 15 | 0  |

    
        Notice `island_key = 0` now shows up for **both** `{1, 2, 4, 5, 6}` and `{12, 13, 14, 15}`
        — two genuinely separate islands collide on the same key purely because of the duplicate rows earlier in the sequence.
    
        **Previous Query: Wrong ans** 
    
        ```sql
        WITH CTE_ISLANDS AS (
            SELECT
                integer_id,
                integer_id - ROW_NUMBER() OVER (ORDER BY integer_id) AS island_key
            FROM integer_table
        )
        SELECT
            MIN(integer_id) AS island_start,

        GROUP BY island_key
        ORDER BY island_start;
        ```

        | island_start | island_end |
        |--------------|------------|
        | 1  | 15 |
        | 2  | 2  |
        | 9  | 12 |
        | 12 | 12 |
    
        `1–15` is nonsense — it silently swallows the real islands `1–2`, `4–6`, and `12–15` into one row because 
        their keys all collided at `0`.
    
    === "Duplicate Records: Correct"
    
        `DENSE_RANK()` only advances when the **value** changes, 
        so duplicate rows share a rank instead of each claiming their own.
    
        **Result:**
    
        | integer_id | dense_rank | island_quantity |
        |------------|------------|------------------|
        | 1  | 1  | 0 |
        | 2  | 2  | 0 |
        | 2  | 2  | 0 |
        | 4  | 3  | 1 |
        | 5  | 4  | 1 |
        | 6  | 5  | 1 |
        | 9  | 6  | 3 |
        | 10 | 7  | 3 |
        | 11 | 8  | 3 |
        | 12 | 9  | 3 |
        | 12 | 9  | 3 |
        | 12 | 9  | 3 |
        | 13 | 10 | 3 |
        | 14 | 11 | 3 |
        | 15 | 12 | 3 |
    
        Every duplicate row now lands on the *same* `island_quantity` as its siblings, 
            and no two unrelated islands share a key.

        ```sql
        WITH CTE_ISLANDS AS (
            SELECT
                integer_id,
                integer_id - DENSE_RANK() OVER (ORDER BY integer_id) AS island_key
            FROM integer_table
        )
        SELECT
            MIN(integer_id) AS island_start,
            MAX(integer_id) AS island_end
        FROM CTE_ISLANDS
        GROUP BY island_key
        ORDER BY island_start;
        ```
    
        **Result (correct):**
    
        | island_start | island_end |
        |--------------|------------|
        | 1 | 2  |
        | 4 | 6  |
        | 9 | 15 |

    
        Counting duplicates within each island
    
        ```sql
        WITH CTE_ISLANDS AS (
            SELECT
                integer_id,
                integer_id - DENSE_RANK()
                    OVER (ORDER BY integer_id) AS island_quantity
            FROM dbo.integers)
        SELECT
            MIN(integer_id) AS island_start,
            MAX(integer_id) AS island_end,
            MAX(integer_id) - MIN(integer_id) + 1 AS island_length,
            COUNT(*) AS row_count
        FROM CTE_ISLANDS
        GROUP BY island_quantity;
        ```
    
        **Result:**
    
        | island_start | island_end | island_length | row_count |
        |--------------|------------|----------------|-----------|
        | 1 | 2  | 2 | 3 |
        | 4 | 6  | 3 | 3 |
        | 9 | 15 | 7 | 9 |
    
        `island_length` counts how many distinct consecutive values the island spans; 
        
        `row_count` counts actual rows, duplicates included. 

        - Where they match (`4–6`), there are no duplicates in that island. 

        - Where `row_count > island_length`: (`1–2`: 3 rows over a length of 2; `9–15`: 9 rows over a length of 7), 
            the gap between the two numbers tells you exactly how many duplicate rows are
            hiding in that island — 1 and 2, respectively.

### 2. Wrong use of Case...When in COUNT(), SUM()  


!!! failure "Wrong"

    ```sql
    COUNT(CASE WHEN condition THEN 1 ELSE 0 END)
    ```
    This counts **all rows**, not just the ones matching the condition 
    — because `COUNT()` counts every **non-NULL** value, and the `ELSE 0` makes every row non-NULL (0 is not NULL).
    
    ==>> So the condition ends up having no filtering effect.

!!! success "Correct — two options"

    **1. Drop the `ELSE`, so non-matching rows become `NULL`:**
    
    ```sql
    COUNT(CASE WHEN condition THEN 1 END)
    ```
    
    `COUNT()` ignores `NULL`s, so only matching rows get counted.

    **2. Or use `SUM()` instead of `COUNT()`, keeping the `ELSE 0`:**
    
    ```sql
    SUM(CASE WHEN condition THEN 1 ELSE 0 END)
    ```
    
    `SUM()` adds up the 1s and 0s directly, so the `ELSE 0` doesn't cause a problem here.
